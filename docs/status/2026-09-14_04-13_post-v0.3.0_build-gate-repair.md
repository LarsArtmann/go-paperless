## e) WHAT WE SHOULD IMPROVE (process + design, not bugs)

1. **Plan from fresh data.** I built my first todo list (per-linter fix steps) from a *stale derivation log*. One wasted planning cycle. Rule: run the authoritative gate on the current tree BEFORE planning fixes. The repo's own lesson ("status reports are point-in-time; re-verify") applies to lint logs too.
2. **Treat line-number mismatch as a stale-data alarm.** The first clue (finding at `example_test.go:21:19` vs decl at line 22) appeared in my very first log read. I noticed it in passing and moved on; acting on it immediately would have re-sequenced the whole session.
3. **Concurrent-session protocol.** Two agents on one repo needs a convention: claim the task, check `git log --since` at start, re-read before every edit (the mtime guard is the last line of defense, not the first).
4. **Verify-then-claim.** Never attribute fix mechanisms in a summary without reading the hunks. "Gate green" is verifiable; "how it got green" needs evidence.
5. **Atomic releases.** The v0.3.0 release commit touched only CHANGELOG.md; the flake version drifted (0.2.0) until this session. Release commit should include: version attr (or git-derived version), CHANGELOG, and gate re-run. Better: derive version from `self.rev`/`self.dirtyRev`/tag so drift is impossible (nix-review checklist item, currently hardcoded).
6. **Document flake surface as it grows.** AGENTS.md lists flake apps but now under-documents packages output. Memory rule: update at moment of discovery.
7. **Restart LSP after external modifications** (or after any session gap) instead of leaving contradictory diagnostics that future sessions must re-adjudicate.
8. **Post-release ritual:** push status → CI green → pkg.go.dev indexed → race run → `--all-systems` note. This repo has already been burned by a pkg.go.dev indexing gap; the ritual should be one command (a flake app or CI job), not memory.
